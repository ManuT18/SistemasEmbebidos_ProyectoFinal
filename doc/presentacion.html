1. Introducción y Contexto

Este documento detalla los avances realizados en el desarrollo del firmware para el Módem FT8 basado en ESP32. El objetivo es crear un dispositivo autónomo capaz de operar en modos digitales sin necesidad de una PC, gestionado íntegramente desde una interfaz web moderna y responsiva.

2. Arquitectura del Sistema Implementada

El sistema se ha diseñado siguiendo un enfoque modular, separando la lógica de negocio (DSP/FT8) de la interfaz de usuario y la gestión de red.

2.1. Componente Web Interface (lib/web_interface)

Se ha encapsulado toda la funcionalidad de red y UI en un componente independiente de ESP-IDF. Esto permite:

  • Desacoplamiento: El main no conoce detalles de HTTP o WebSockets.
  • Reusabilidad: El componente puede ser portado a otros proyectos.
  • Mantenibilidad: Código C y HTML/JS separados lógicamente.

3. Características Implementadas

3.1. Punto de Acceso y Servidor Web

El ESP32 inicia su propia red Wi-Fi (AP) llamada ESP32-FT8-Modem. Al conectarse, el usuario accede a una Single Page Application (SPA) servida directamente desde la memoria flash del microcontrolador.

3.2. Gestión de Sesión y Persistencia

Para mejorar la experiencia de usuario (UX), se implementó un sistema de "sesión" utilizando localStorage del navegador:

  • Login: El operador ingresa su Señal Distintiva y Grid Locator.
  • Persistencia: Los datos se guardan localmente. Al recargar la página o reconectar, el sistema hace "auto-login".
  • Logout: Un botón dedicado permite cerrar la sesión y limpiar los datos almacenados.

3.3. Comunicación en Tiempo Real (WebSockets)

La comunicación entre el navegador y el ESP32 es bidireccional y asíncrona mediante WebSockets:

  • Control: Envío de comandos (Toggle LED, Consultas).
  • Monitoreo: Recepción de logs y estados en tiempo real.
  • Eficiencia: Evita el polling constante (AJAX), reduciendo la carga en la red y la CPU.

3.4. Sincronización de Tiempo (RTC)

El protocolo FT8 requiere precisión temporal absoluta. Ante la ausencia de un módulo GPS dedicado:

  • Estrategia: Se confía en la precisión del reloj del dispositivo cliente (Smartphone/PC).
  • Justificación: Los smartphones modernos mantienen su reloj sincronizado con alta precisión mediante la red celular (LTE/5G) o NTP.
  • Implementación: El navegador envía su timestamp UTC al ESP32. Si hay internet disponible (Split Tunneling), se intenta verificar con una API externa; de lo contrario, se usa la hora del sistema del teléfono como fuente confiable.

3.5. Modo Ahorro de Energía (Light Sleep)

Para extender la autonomía de la batería sin perder conectividad, se implementó un sistema de gestión de energía conmutable:

  • Activación: Botón azul "Modo Ahorro" en la interfaz.
  • Funcionamiento: El ESP32 entra en modo WIFI_PS_MAX_MODEM, apagando el radio WiFi entre balizas DTIM.
  • Periféricos: Se apagan indicadores visuales (LED) y se reduce la frecuencia de tareas no esenciales.
  • Experiencia: El dispositivo sigue respondiendo a peticiones web, aunque con una ligera latencia adicional, logrando un equilibrio entre usabilidad y consumo.

El componente web no accede directamente a las variables globales del sistema. Se utiliza un patrón de Inversión de Control mediante callbacks:

    // En main.c: Registramos las funciones que proveen los datos
    web_interface_register_data_providers(provide_callsign, provide_grid);
}

// ---------------------------------------------------------

// En web_interface.c: Cuando el cliente pide datos, invocamos el callback
if (g_get_call_cb) {
    char buf[32];
    g_get_call_cb(buf, sizeof(buf)); // Obtenemos el dato de forma segura
    // ... enviar por WebSocket

5. Vinculación con la Asignatura

El desarrollo de este proyecto integra y aplica múltiples conceptos centrales de la materia Sistemas Embebidos:

  • Sistemas Operativos de Tiempo Real (RTOS):
    • Uso de FreeRTOS (nativo en ESP-IDF) para la gestión de tareas concurrentes.
    • La tarea del Servidor Web corre en paralelo con el bucle principal, y a futuro convivirá con tareas críticas de DSP (Procesamiento Digital de Señales).
  • Periféricos y Entradas/Salidas (GPIO):
    • Control directo de hardware (LED indicador) mediante la API de drivers de bajo nivel (driver/gpio.h).
  • Protocolos de Comunicación:
    • TCP/IP y WiFi: Implementación de un stack de red completo en un microcontrolador.
    • HTTP/WebSockets: Desarrollo de aplicaciones IoT conectadas, superando el modelo tradicional de "polling".
    • UART: Uso para depuración y logging del sistema.
  • Toolchain y Cross-Compilation:
    • Uso del framework ESP-IDF y el sistema de construcción CMake.
    • Compilación cruzada desde el host (PC) hacia el target (ESP32).
  • Sistemas de Archivos en Flash:
    • Embebido de recursos estáticos (HTML/CSS/JS) directamente en la memoria de programa del microcontrolador (mecanismo de EMBED_FILES de CMake), simulando un sistema de archivos de solo lectura.

6. Análisis de Consumo Energético

Para garantizar la autonomía del módem en operaciones de campo (portable), se ha realizado un análisis teórico de la duración de la batería en modo Light Sleep / Modem Sleep. En este modo, el ESP32 mantiene la conexión WiFi activa pero apaga la CPU entre balizas (beacons), reduciendo el consumo.

Parámetros de Cálculo

  • Consumo Estimado (DevKit): ~80 mA (Incluye regulador LDO, LED de power, USB-UART).
  • Consumo Optimizado (Custom PCB): ~40 mA (Solo ESP32 + Periféricos esenciales).
  • Batería Base: Celda Li-Ion 18650 estándar (3000 mAh / 3.7V).

Escenarios de Batería (Estimación para DevKit - 80mA)

1. Una Celda (1S1P) - 3000 mAh
Configuración básica. Voltaje directo a regulador 3.3V.
~37 Horas
2. Dos Celdas en Paralelo (1S2P) - 6000 mAh
Doble capacidad, mismo voltaje. Ideal para autonomía extendida sin conversores extra.
~75 Horas (3 Días)
3. Dos Celdas en Serie (2S1P) - 3000 mAh (7.4V)
Mayor voltaje. Requiere conversor DC-DC (Buck) eficiente (~90%) para aprovechar la energía extra.
~68 Horas

Nota: Los cálculos asumen una descarga útil del 85% de la capacidad nominal y un consumo constante promedio. El modo "Deep Sleep" real (sin WiFi) extendería esto a meses, pero perdería la conectividad inmediata.
